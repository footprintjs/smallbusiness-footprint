# Integrate after-sales without hiding the business boundary

Import browser-safe types/policy from `smallbusiness-footprint/aftersales`. Backend execution uses `createAfterSalesService` from `smallbusiness-footprint/aftersales/runtime`. It runs real FootPrintJS charts; it does not install a payment vendor, queue or database.

Supply `repository`, `payments`, trusted `authorizer`, `storeId`, optional `policy`, `now`, `generateId` and `onTrace`. Call `request(command, context)` for a cancellation/return request and `action(command, context)` for an owner operation. The HTTP host establishes customer ownership and owner identity; neither comes from command text.

## Policy and state rules

The default policy permits cancellation before a shipping/label claim wins and returns within 30 days of recorded delivery with unworn condition and tags confirmed. `validateAfterSalesPolicy` validates store-specific windows, requirements and enabled flags. Each case snapshots its policy; changing configuration does not rewrite existing cases.

Owner approval is required. Return approval authorizes return shipment only: actual receipt and accepted inspection precede refund. Amounts are positive integer cents; item selection uses stable saved-order line IDs and whole quantities. A full cancellation can mark the order cancelled. A partial cancellation retains a fulfillment hold for owner review so an older shipping snapshot cannot send cancelled quantities. Already-created labels require manual carrier review; the library does not claim an atomic carrier void.

## Authoritative repository and payment ports

The repository must atomically deduplicate requests, allocate quantities, race cancellation holds against shipping claims, compare case/order versions, and reserve refunds against captured money minus prior refunds and every pending reservation. The chart is not a substitute for those durable transactions.

A durable refund intent and stable key are saved **before** calling a provider. Pending/unknown results retain the reservation and reconcile with the same key or refund ID. Missing provider evidence is not permission to create a new refund. The provider adapter must refuse replay after its idempotency-retention window; confirmed failure stays distinct from unknown. No fresh key or business retry is generated by diagnostics.

Restocking is a separate exactly-once host transaction after confirmed refund and accepted return inspection. A cancellation hold is not automatically released by refund/restock completion. Hosts own durable recovery, credentials, notifications and return-label costs.

## Decisions and backward investigation

The unreleased working candidate makes real after-sales control choices visible as native decider stages and records only safe producer booleans needed by those choices. Private predicates are evaluated from request-local state; customer reasons, owner notes, identities, addresses, provider payloads and payment IDs do not become shared-state debugging shortcuts.

Follow the actual native decision and branch destination, then its safe producer and private predicate source. A static descriptor is not an observed decision. If a repository/payment call is opaque, inspect the host implementation or actual boundary evidence before asserting a cause. This source change preserves business behavior and does not retroactively add decisions or producer evidence to old traces. The published registry 1.1.0 does not acquire the candidate refactor without a new build/release.

After-sales retains full native read/write/commit capture on this safe fact surface. It does not expose the underlying private case or provider object. Semantic subflows explicitly isolate state with empty input/output mappings. `load-request-order` produces `requestKind` locally; its selected policy branch publishes `policySatisfied`, and `request-policy-eligible` controls persistence. Actual guards retain the selected safe `branchResult` tag in their own commit.

Item loops stay in their scope and are bounded at 100, without creating a scope per item. `lineCheck` and `restockLineCheck` include the current position with eligibility, preserving a distinct actual writer even when repeated eligibility booleans are equal. Inspect both the native decision and its recorded producer when walking backward; these safe facts do not reveal private predicate inputs or prove an upstream cause. Composed `executeServiceFlow` recording remains a separate summary-retention path. For actual saved mounted scopes and bounded-loop cause queries, use [the after-sales cause reader](AFTERSALES-CAUSE.md).

## Caller controls and optional evidence

`executionOptions: ({ flowId }) => controls` forwards trusted payload-free engine controls such as cancellation, deadline and trace correlation. The engine validates/enforces them. This does not authorize a refund, restock, label or retry.

`onTrace` receives the native snapshot, chart structure, narrative and safe metadata. Hosts own authenticated store-scoped persistence and retention. Optional `withBoundaryScope(port, work)` binds the real provider recorder to that execution; it does not introduce a global context. Optional `recordSink` and `recordSinkFlushTimeoutMs` attach native recording/drain behavior. An attached sink, locator or completed drain is not a durable acknowledgement. Recording failure cannot reverse a saved case or provider acknowledgement.

See [provider evidence](PROVIDER-EVIDENCE.md) for sink, partial-prefix and uncertainty contracts. Test adapters against real durable storage/provider sandbox behavior separately from the local fixture suite.

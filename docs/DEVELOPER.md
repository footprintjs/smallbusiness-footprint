# Optional source-backed developer context

**Unreleased working candidate.** These exports require this checkout or its newly built local package. Published registry 1.1.0 does not contain them yet. They are optional tooling, not a new business runtime or diagnosis authority.

## Describe a service without building its chart

The separate `smallbusiness-footprint/developer` entry exports `describeDeveloperService`, `describeDeveloperServices`, `resolveDeveloperSource` and their types. It reads static declarations and a caller-trusted build manifest; it does not call chart builders, terminology resolvers, application operations or providers. It is not re-exported through the main runtime or `/metadata` entry.

```js
import { describeDeveloperService } from 'smallbusiness-footprint/developer';
import manifest from 'smallbusiness-footprint/developer/source-manifest.json'
  with { type: 'json' };

const description = describeDeveloperService('create-order', { manifest });
console.log(description?.coverage);
console.log(description?.source);
```

Built-in descriptions expose the library request envelope and its declared input fields. Their authoritative operation remains opaque and `completeApplication` stays false. A description for `create-order` is not a complete checkout implementation. The existing runtime `describeService` API builds a chart; it is distinct from this static catalog.

Pass the same trusted configured `flowRegistry` and optional `businessType` used by the application to describe a selected custom variant. The optional `ActionFlowEntry.developer` registration contains static default/variant descriptions, source selectors, stage references, field declarations and operation ownership. That registration adds no runtime catalog method. A custom builder without a matching descriptor stays unknown; no description is inferred by executing it. Treat descriptor objects as trusted application configuration, not customer input.

## Understand the manifest claim

`source-manifest.json` is generated by `pnpm build` from production TypeScript syntax. It has schema version 1 and scope `source-only-static-syntax`. Each canonical source file has its SHA-256, parse status, package path and exact function/callback/expression/state-access spans. Unresolved syntax is not silently promoted to a complete implementation.

`sourceTreeSha256` identifies actual build-source content; it is not a Git-parent revision, a signature or proof that a package came from a trusted publisher. Pure resolution returns `status: 'build-manifest'` with `freshness: 'not-checked'` and `authenticity: 'caller-trusted-build'`. Field contracts remain `verification: 'declared'`. A source hash or possible writer cannot establish that code executed, produced a value or caused a failure.

Unit `start`/`end` offsets are JavaScript UTF-16 string positions, with exclusive end. `byteStart`/`byteEnd` are separate UTF-8 positions. Keep these coordinate systems distinct when opening or editing original source.

The package retains one production TypeScript copy under `dist/source/`, with actual installed paths declared as `packagePath`. JavaScript/declaration maps point to that copy. `__tests__`, `__fixtures__` and `.test.ts`/`.spec.ts` files are excluded; benchmark reports are not inputs. The explicit public `/testing` helper implementation is production package code, distinct from those excluded test files. Its observed counters/private scenario state still must not enter diagnosis records. In a checkout, current live `src/` must take precedence over an older packaged copy for freshness checks.

## Read current source explicitly in Node

`smallbusiness-footprint/developer/node` exports `loadDeveloperSourceManifest`, `createDeveloperSourceReader` and `DeveloperBudgetError`. The optional reader does not import or execute application modules. It accepts only canonical production TypeScript paths such as `src/flows/shared/businessFlow.ts` from the manifest, prefers live checkout source, otherwise reads the manifest's exact `dist/source/...` copy, and rejects root-escaping symlinks.

```js
import { createDeveloperSourceReader, DeveloperBudgetError }
  from 'smallbusiness-footprint/developer/node';

const reader = await createDeveloperSourceReader({ characterBudget: 4000 });
try {
  const version = await reader.verify('src/flows/shared/businessFlow.ts');
  console.log(version); // current, stale or unknown; sourceChars is zero
  const handler = await reader.inspect({
    file: 'src/flows/shared/businessFlow.ts',
    stageId: 'execute-operation', role: 'handler',
  }, { includeSource: true });
  console.log(handler);
} catch (error) {
  if (!(error instanceof DeveloperBudgetError)) throw error;
  // No partial source/hash payload was returned for the oversized response.
}
```

By default the root is the package containing the reader. Pass `root` to read a specific trusted checkout/package, or `manifest` to supply an independently trusted build manifest. `loadDeveloperSourceManifest(root?)` reads `dist/developer/source-manifest.json`. An external application's source is not automatically admitted by the SMB manifest.

The reader methods are:

| Method | Result |
| --- | --- |
| `verify(file, expectedHash?)` | `current`, `stale` or `unknown`; zero source characters; compares actual module bytes with the manifest and optional SHA-256 |
| `inspect(selector, { includeSource? })` | Metadata by default; explicit exact unit/module source only on request, after current-byte and range/hash proof |
| `describe(actionId, businessType?)` | Bounded static metadata for the same configured registry, not execution or fresh source verification |

Selectors accept `file` with optional `symbol`, `unitId`, `stageId` and `role`. Ambiguous or unsupported selectors stay unknown. With no unit selector, inspection describes the complete module; requesting it can exceed the budget. Stale source is reported without returning a mismatched old body. A successful hash check proves version correspondence, not prior delivery, release authenticity, runtime data lineage or business semantics.

The default character budget is 4000 **per reader instance**. Every returned response charges its complete `JSON.stringify(result).length`, including status, hashes and accounting fields. `responseChars`, `cumulativeChars` and `remainingChars` are returned together. Oversized responses throw the constant `DeveloperBudgetError` with code `DEVELOPER_BUDGET_EXHAUSTED` before returning that response's data. There is no silent truncation or free hash/status result. A host controlling multiple readers must own any wider session budget; this helper does not claim a cross-process ledger.

## Keep runtime and package cost separate

The static catalog and explicit Node reader are separate optional imports; they are not pulled into the main runtime/metadata graph just by being exported. This avoids an automatic runtime dependency on developer tooling. The retained source and manifest still occupy installed package bytes, so optional imports do not mean zero npm download/storage cost. The AST parser is build tooling, not an application runtime parser.

Benchmarks, reports, raw model logs and application variants belong in a separate research repository. This library does not bundle those artifacts or claim a model-development performance gain from these source tools.

Use [the agent guide](AGENT-GUIDE.md) to combine current source with actual retained runtime evidence. Provider internals, durable effects, absent branches and incomplete recordings remain outside what a static source catalog can prove.

## Generate README chart views from runtime definitions

The working candidate also builds [the registered flow index](flows/README.md), compact root/folder README sections and linked full subflow README pages from the actual runtime builders. After-sales runtime and documentation use one internal chart registry; standard service views enumerate the actual default registry. FootPrintJS's native `toMermaid()` supplies the topology. Verified native node metadata adds decision diamonds, actual branch-key labels, subflow boxes and explicitly dashed continuations after branch completion. Both node identities and the complete edge multiset are checked against the raw SDK output; annotations change no topology. No stage, application operation, provider, custom builder or lazy resolver is run.

`npm run build` refreshes these views. `npm run docs:flows` writes them explicitly, and `npm run check:flow-docs` freshly compiles source in a temporary directory and fails if any generated section/page or membership is stale. CI runs that check before build so generation cannot silently hide an outdated committed diagram. Handwritten README text outside the generated markers is preserved.

The root section is bounded at 2,000 characters and folder overviews at 4,000; all subflow views remain available through drill links. Larger individual graphs fail their documented budget instead of losing nodes. Repeated pages share matching native topology only. The manifest retains every actual mount context and the stable prefix-alias mapping; it does not equate private helper semantics. Production inputs, generator files and SDK/compiler versions are hashed without hashing generated documentation back into itself.

Chart links target canonical checkout sources, so GitHub follows the same branch being reviewed. In an installed package use `developer/node` with the logical `src/...` ID; the manifest resolves its single retained `dist/source/...` copy. Rebuild after editing source. These static diagrams and possible field writers are navigation aids, not runtime lineage or measured token savings. The existing public source reader still cannot select every object-method hook body; ordinary source reads remain appropriate.
